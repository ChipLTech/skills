# Main-to-Main Upgrade Stable Decisions

shared_contract: vllm-dlc-contract/v1

Main-to-Main Upgrade owns exact upstream target identity, ordered Verified vLLM Alignment candidate recovery, exhaustive global compatibility impact, read-only manifest impact, mandatory regression assignments, child aggregation, and no-finalize reporting. It delegates all model-specific adaptation one-way to Model Adaptation.

Historical mandatory evidence outranks an explicit Git pin, which outranks a correlated candidate. Checkout state, installation metadata, README text, and time correlation never establish a Verified vLLM Alignment without complete mandatory evidence.

Every changed upstream surface must be an affected dependency, a new dependency candidate, or confirmed irrelevant. Unknown impact must be zero. Manifest output is a future-change report and never an applied mutation in this candidate.

Exact-HEAD static inspection can establish that a source surface is absent. It becomes a demonstrated necessary fix for a target workload only after an exact-artifact runtime experiment reaches the target failure boundary and confirms necessity. During delta classification, record that experiment as the validation assignment and map it through the existing v1 dependency IDs; consume its result during child aggregation. Because v1 has no independent necessity-verdict field, identity closure without eligible bounded diagnosis remains `not_verified`. A historical patch not appearing verbatim in main, a failed mixed-version stack, or a repository receiving no patch cannot establish workload necessity. Existing replacement behavior is confirmed present or superseded; source present but consumer/descriptor/DLC Custom Kernel/toolchain/native identities mismatched is artifact or ABI pairing.

For each global surface, preserve repository owner, consumer owners, change kind, paired dependency identities, and validation owner inside the existing v1 evidence/reason fields; this decision does not extend the shared schema or action vocabulary. Investigation can cover more repositories than the final change. Split future PR units by repository responsibility and one principal purpose, not by the number of delivery patch files.

## Tested And Publication Identities

The Tested Revision is the exact checkout and artifact graph that produced validation evidence. A Publication Candidate is a delivery representation constructed from the current target main with only the approved scoped delta. Preserve the Tested Revision as primary evidence; do not rewrite it in place merely to obtain a one-commit PR. Record candidate base and commit SHAs, clean worktree state, complete scoped diff/tree identity, excluded paths, and the gates rerun against that candidate.

Patch Equivalence is scoped evidence, not acceptance transfer. Stable patch-id can support equivalence across squash or rebase, but it ignores commit metadata and does not prove that a changed base resolves dependencies, ABI, toolchain, native artifacts, or runtime behavior identically. Base movement requires rebuilding the candidate and rerunning every affected source/contract gate; any possible artifact-graph change also requires the corresponding build and runtime gates before evidence can be associated with the candidate.

When publication is proposed, it has an independent concurrency and authorization boundary. Capture the current target-main SHA and existing PR-branch tip as exact lease expectations. A mismatch blocks publication and requires candidate reconstruction plus affected revalidation. Rewriting a remote PR branch requires separate explicit authorization and exact expected-old-SHA `--force-with-lease`; an unleased force push is never an eligible path. A read-only impact analysis with no proposed publication reports no candidate rather than inventing one. This read-only, no-finalize Skill reports the gate and blocker only; it never creates the candidate, commits, rewrites history, or pushes.
